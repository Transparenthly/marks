# Docker: сети и связь между контейнерами

## Базовый принцип изоляции

Каждый контейнер — это процесс со **своим сетевым namespace**: собственные интерфейсы, свой IP, своя таблица маршрутизации, свой `/etc/resolv.conf`.

Практическое следствие: `localhost` внутри контейнера — это **сам контейнер**, а не хост-машина и не соседний контейнер. Самая частая ошибка новичка — прописать `HOST=localhost` для связи между контейнерами.

---

## Типы сетей

| Драйвер | Назначение |
|---|---|
| `bridge` (default) | Виртуальный мост, контейнеры получают внутренние IP |
| `host` | Контейнер использует сетевой стек хоста без изоляции |
| `none` | Сети нет |
| `overlay` | Связь контейнеров на **разных** физических машинах (Swarm) |

### Критическое различие: default bridge vs user-defined bridge

**Default bridge** (сеть `bridge`, куда попадает контейнер без `--net`):
- **DNS отсутствует** — связь только по IP
- IP выдаётся динамически и меняется при перезапуске
- Устаревший способ связи — флаг `--link`

**User-defined bridge** (создана через `docker network create`):
- Docker поднимает **встроенный DNS-сервер** на адресе `127.0.0.11`
- Имена контейнеров автоматически резолвятся в текущие IP
- IP меняется — имя остаётся стабильным

**Вывод:** в конфигах всегда используй имя контейнера, не IP.

```bash
docker network create my_net
docker run -d --name postgres --net=my_net postgres
# другой контейнер обращается по хосту: postgres
```

## Публикация портов: -p

### Синтаксис

```
-p <порт_на_хосте>:<порт_в_контейнере>
-p <IP_на_хосте>:<порт_на_хосте>:<порт_в_контейнере>
```

### Когда -p нужен, а когда нет

| Направление | Нужен ли -p |
|---|---|
| контейнер ↔ контейнер в одной сети | **нет**, все порты видны напрямую |
| хост → контейнер | **да** |
| внешняя сеть → контейнер | **да** |

Это важно: postgres и clickhouse в одной сети общаются на 5432/9000 без всякой публикации портов.

## Bind-адреса: 0.0.0.0 vs 127.0.0.1

### Что означает bind

Программа привязывается не «к порту вообще», а к **конкретному интерфейсу**. У любой машины/контейнера минимум два интерфейса:

| Интерфейс | Адрес | Кто достучится |
|---|---|---|
| `lo` (loopback) | `127.0.0.1` | только процессы внутри этой же машины/контейнера |
| `eth0` | внутренний IP | всё снаружи через сеть |

`0.0.0.0` — не адрес, а указание **«слушать на всех интерфейсах»**.

### Классическая ловушка

```dockerfile
ENTRYPOINT ["gunicorn", "--bind", "127.0.0.1:8000", "wsgi:app"]
```
Даже с `-p 8000:8000` снаружи будет `Connection refused`. Почему: проброс доставляет трафик на `eth0` контейнера, а приложение слушает только loopback. Loopback **никогда не пересекает границу контейнера** — twoй `127.0.0.1` и `127.0.0.1` контейнера это два разных изолированных интерфейса.

Внутри контейнера при этом работает только `curl localhost:8000`, а `curl <IP_контейнера>:8000` — нет.

**Правило:** в контейнере всегда биндись на `0.0.0.0`.

### Занимается пара (IP, порт), а не порт

Уникальным должно быть **сочетание**, поэтому это работает без конфликта:
```bash
docker run -d -p 127.0.0.1:8080:80 nginx      # только loopback
docker run -d -p 192.168.1.42:8080:80 nginx   # только Wi-Fi интерфейс
```

А это упадёт с `port is already allocated`:
```bash
docker run -d -p 8080:80 nginx                # занял 0.0.0.0:8080 = ВСЕ интерфейсы
docker run -d -p 127.0.0.1:8080:80 nginx      # ОШИБКА
```

**Практическое применение:** bind на `127.0.0.1` — простейший способ ограничить доступ к сервису (админка, отладочный порт). Пакет физически не может прийти на loopback снаружи, надёжнее файрвола.

### Доступ из локальной сети

`-p 80:80` биндит на `0.0.0.0` хоста → сервис доступен по **всем** адресам машины, включая Wi-Fi (`192.168.x.x`). Телефон в той же сети откроет `http://192.168.x.x`.

Узнать свой IP:
```bash
ipconfig getifaddr en0        # macOS
ifconfig | grep "inet "       # универсально
```
На macOS Wi-Fi интерфейс — `en0`/`en1` (не `wlp9s0`, это Linux-именование).

Ограничение: `192.168.x.x`, `10.x.x.x`, `172.16-31.x.x` — приватные диапазоны, не маршрутизируются в интернете. Только локальная сеть.

## Внутреннее устройство: veth, бриджи, namespace

### veth-пара

Виртуальный «патч-корд» с двумя концами: один внутри сетевого namespace контейнера (виден как `eth0`), второй на хосте — воткнут в бридж. Всё, что уходит в один конец, выходит из другого. Так трафик пересекает границу изоляции.

### Бридж

Виртуальный **коммутатор** на хосте. Каждая user-defined сеть = свой бридж со своей подсетью:
- сеть A → бридж `172.18.0.1`, контейнеры `172.18.0.x`
- сеть B → бридж `172.19.0.1`, контейнеры `172.19.0.x`

Бридж имеет собственный IP (`.0.1`) — это gateway для контейнеров сети.

### Нюанс: gateway или switch?

Когда два контейнера **в одной подсети**, шлюз не участвует как хоп. Работает ARP: контейнер узнаёт MAC получателя, бридж коммутирует кадр по MAC на канальном уровне (L2).

Шлюз становится настоящим шлюзом только при выходе **наружу** подсети (`ping 8.8.8.8`) — тогда пакет идёт на `172.18.0.1`, дальше через NAT на `eth0` хоста.

Подтверждение в выводе ping: `ttl=64` (полное, не уменьшенное) = маршрутизатор не проходили.

### Именование интерфейсов в контейнере

- `lo` — loopback, всегда
- `eth0` — первая подключённая сеть
- `eth1` — вторая, и т.д.

Подключение к второй сети:
```bash
docker network connect second_net имя_контейнера
```
Синтаксис: `docker network connect <сеть> <контейнер>`.

**Нюанс:** номера присваиваются в порядке подключения и не гарантированно стабильны между перезапусками. Никогда не завязывайся на имя интерфейса — используй DNS-имена контейнеров.

### Мультисетевая изоляция

```
frontend_net:  nginx ←→ app
backend_net:            app ←→ postgres
```
`app` подключён к обеим, видит всех. `nginx` **физически не может** достучаться до postgres — разные подсети, общего бриджа нет. Изоляция на сетевом уровне, не «договорённость».

Ограничивает ущерб при компрометации: взломав nginx, атакующий не получает сетевого доступа к базе.

## Полный путь пакета: ping из контейнера в контейнер

1. **Резолвинг имени.** Контейнер читает `/etc/resolv.conf` → там `nameserver 127.0.0.11` (встроенный DNS Docker). Спрашивает IP для имени `c2`.
2. **DNS отвечает.** Docker возвращает адрес `c2` **в общей сети**. Если общей сети нет — имя не резолвится вообще.
3. **Маршрутизация.** Ядро сравнивает адрес назначения со своей подсетью. Своя подсеть → шлюз не нужен. Чужая → на gateway.
4. **ARP.** Широковещательный запрос «у кого этот IP» → получатель отвечает MAC-адресом. Результат кэшируется.
5. **Выход через veth.** Пакет уходит из `eth0` контейнера, мгновенно появляется на хосте.
6. **Коммутация на бридже.** Бридж смотрит MAC назначения, отправляет кадр в нужный порт.
7. **Доставка.** Кадр приходит на `eth0` получателя. Ответ идёт обратным путём.

## Переменные окружения для конфигурации

Образ неизменяем — конфигурация передаётся снаружи через `-e` при запуске.

### Официальный образ postgres

| Переменная | Назначение |
|---|---|
| `POSTGRES_USER` | суперпользователь (default: `postgres`) |
| `POSTGRES_PASSWORD` | **обязательна**, без неё контейнер не стартует |
| `POSTGRES_DB` | создаваемая база |

**Нюанс:** переменные срабатывают только при **первой** инициализации пустого хранилища. Перезапуск с существующим volume и другим паролем ничего не изменит.

```bash
docker run --rm -d \
  --name postgres \
  --net=my_net \
  -e POSTGRES_USER=myuser \
  -e POSTGRES_PASSWORD=mypassword \
  -e POSTGRES_DB=mydb \
  postgres
```

Приложение подключается:
```bash
docker run --rm \
  --net=my_net \
  -e PG_HOST=postgres \      # ИМЯ КОНТЕЙНЕРА, не localhost
  -e PG_USER=myuser \
  -e PG_PASSWORD=mypassword \
  -e PG_DATABASE=mydb \
  my_app
```

Postgres инициализируется несколько секунд — приложение, запущенное сразу, может поймать `Connection refused`. Проверяй `docker logs postgres` на строку `database system is ready to accept connections`.

## Практические команды

### Сети
```bash
docker network ls                    # список сетей
docker network create my_net         # создать (драйвер bridge по умолчанию)
docker network inspect my_net        # кто подключён, какие IP
docker network connect net2 mycontainer
```

Сети **не создаются автоматически** — `--net=nonexistent` даёт ошибку `network not found`.

### Контейнеры
```bash
docker ps                # запущенные
docker ps -a             # включая остановленные
docker logs имя          # вывод контейнера
docker stop имя
docker rm имя
docker rm -f имя         # принудительно: stop + rm одной командой
```

`--rm` при запуске = автоудаление после остановки. Без него контейнер остаётся и **блокирует имя** (`Conflict. The container name is already in use`).

### Выполнение внутри контейнера
```bash
docker exec -it имя bash                    # интерактивный shell
docker exec -it postgres psql -U myuser -d mydb
docker exec -it имя ls /sys/class/net       # список интерфейсов
```
`-i` (stdin открыт) + `-t` (псевдотерминал) — почти всегда идут парой.

Всё после имени контейнера выполняется **внутри него**, не на хосте.

### Диагностика сети без утилит

Минималистичные образы не содержат `ip`, `ifconfig`, `ping`. Читаем напрямую из ядра:
```bash
docker exec -it имя ls /sys/class/net       # имена интерфейсов
docker exec -it имя cat /proc/net/dev       # + статистика
```
`/proc` и `/sys` — псевдо-ФС, генерируемые ядром на лету. **На macOS их нет** — это Linux-специфика (macOS BSD-подобная).

Установка утилит внутрь (пропадёт при пересоздании контейнера):
```bash
docker exec -it имя bash
apt update && apt install -y iputils-ping iproute2 tcpdump
```
`ip` из `iproute2` предпочтительнее устаревшего `ifconfig` из `net-tools`.

### Просмотр трафика
```bash
# Терминал 1 — слушаем
docker exec -it c1 tcpdump -i eth0 icmp

# Терминал 2 — генерируем
docker exec -it c1 ping -c 4 c2
```
tcpdump держит терминал до `Ctrl+C`. Вывод: пары `ICMP echo request` / `echo reply` с временными метками.

**На macOS** бриджи хоста не видны через `ifconfig` — Docker Desktop держит Linux-подсистему в виртуальной машине. Из контейнера картина полная.

## Типовые ошибки и их симптомы

| Ошибка | Причина |
|---|---|
| `pull access denied for 00rm` | опечатка во флаге → Docker принял его за имя образа. Первое слово без дефисов = образ |
| `network X not found` | сеть не создана, нужен `docker network create` |
| `container name already in use` | старый контейнер занимает имя, нужен `docker rm -f` |
| `port is already allocated` | конфликт bind, проверь `docker ps` колонку PORTS |
| `could not translate host name` | контейнеры в разных сетях, проверь `docker network inspect` |
| `Connection refused` при связи | сервис не успел стартовать, либо bind на `127.0.0.1` вместо `0.0.0.0` |
| `password authentication failed` | расхождение `POSTGRES_*` и переменных приложения |

### Warning про платформу на Apple Silicon
```
WARNING: The requested image's platform (linux/amd64) does not match
the detected host platform (linux/arm64/v8)
```
Образ собран под Intel, запускается через эмуляцию. Работает, но медленнее. Иногда есть ARM-версия под другим именем (`clickhouse/clickhouse-server` вместо устаревшего `yandex/clickhouse-server`).
