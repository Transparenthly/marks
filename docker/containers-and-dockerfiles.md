# Docker: команды, Dockerfile и флаги — подробный конспект

Формат: команда → что делает → **что ломается и почему**, если применить не так.

---

## Часть 1. Работа с контейнерами

### Запуск

```
docker run <образ>
docker run -d <образ>
docker run -it <образ>
docker run --name <имя> <образ>
```

**Ключевой подводный камень: контейнер не всегда "живёт" после запуска.**

То, что происходит после `docker run`, зависит не только от флагов, но и от того, что делает образ **по умолчанию** (его `ENTRYPOINT`/`CMD`):

- Образы вроде `python`, `node`, а также `golang` (на базе Debian) без указанной команды запускают интерактивный интерпретатор/оболочку, которая **ждёт ввод из stdin**. Если запускать в фоне (`-d`, без `-it`) — stdin не подключён, процесс сразу получает EOF ("конец файла") и завершается. Контейнер мгновенно уходит в статус `Exited`, даже если ты указал `-d`.
- Образы вроде `nginx`, `redis` по умолчанию запускают сам сервер как процесс на переднем плане — он не завершается сам, контейнер остаётся `Up`.
- Вывод: если контейнер "падает" сразу после `docker run -d <образ>` — проверь, что образ вообще делает по умолчанию. Если нужно, чтобы он жил, придётся дать ему бесконечную команду, например:
  ```
  docker run -d <образ> tail -f /dev/null
  ```

### Просмотр

```
docker ps            # только работающие
docker ps -a         # все, включая остановленные
docker images        # список образов
docker images -q     # только ID (quiet)
docker images --no-trunc   # полные ID, без обрезки
```

**Подводный камень:** `docker images <имя>` — это **фильтр** по локальным образам, а не попытка их скачать. Если образа с таким именем нет — команда просто вернёт пустой список, **без ошибки**. Ошибка была бы у `docker pull <имя>` или `docker run <имя>`, где Docker реально пытается достучаться до реестра.

### Остановка и удаление

```
docker stop <контейнер>
docker rm <контейнер>
docker rm -f <контейнер>
docker rmi <образ>
```

**Подводный камень №1: `docker rm` без `-f` не трогает работающие контейнеры.**
Если контейнер в статусе `Up`, `docker rm` откажется его удалять и выдаст ошибку — он **не останавливает контейнер автоматически**. Нужно либо сначала `docker stop`, либо сразу `docker rm -f` (это форсированно останавливает и удаляет за одну команду).

**Подводный камень №2: `docker rmi` не даст удалить образ, который использует хоть один контейнер** (даже остановленный, даже просто существующий, необязательно работающий):
```
Error response from daemon: conflict: unable to delete <образ> (must be forced) - container ... is using its referenced image
```
Решение: сначала удали контейнер(ы), которые на него ссылаются, либо добавь `-f`.

**Подводный камень №3: один образ может иметь несколько тегов.**
Например, `golang:1` и `golang:latest` часто указывают на один и тот же физический образ (одинаковый IMAGE ID). Если удалить один тег (`docker rmi golang:1`) — реально просто "отвяжется" имя (`Untagged: golang:1`), а сами данные образа останутся доступны под вторым тегом. Место на диске не освобождается, пока жив хоть один тег.

**Подводный камень №4: `--rm` при запуске меняет то, что видно в `docker ps -a`.**
Флаг `--rm` в `docker run --rm <образ>` означает: как только контейнер останавливается — он **автоматически и сразу удаляется**, а не просто переходит в Exited. Такие контейнеры вообще не появятся в `docker ps -a`. Это важно при подсчёте "сколько всего контейнеров было создано" — если использовался `--rm`, ответ может быть меньше, чем кажется на первый взгляд.

### Вход внутрь контейнера

```
docker exec -it <контейнер> bash
docker exec -it <контейнер> sh
```

**Подводный камень:** `exec` работает только с **уже запущенным** (`Up`) контейнером. Если контейнер в статусе `Exited` — получишь ошибку:
```
Error response from daemon: container ... is not running
```
Сначала нужно `docker start <контейнер>`, а уже потом `exec`. Само создание контейнера (`docker run`) не гарантирует, что он "живой" на момент, когда ты пытаешься в него зайти — см. пункт про запуск выше.

### Логи и информация

```
docker logs <контейнер>
docker logs -f <контейнер>     # -f = follow, читать в реальном времени
docker inspect <контейнер>
docker history <образ>         # список слоёв образа и их размер
```

## Часть 2. Dockerfile и сборка образов

### Базовые инструкции

| Инструкция | Что делает |
|---|---|
| `FROM <образ>` | Базовый образ. Обязательно первая инструкция файла |
| `WORKDIR <путь>` | Рабочая директория внутри контейнера для всех следующих команд |
| `COPY <источник> <назначение>` | Копирует файл/папку с хоста (из контекста сборки) в образ |
| `RUN <команда>` | Выполняется **во время сборки** образа, создаёт новый слой |
| `ENTRYPOINT ["..."]` | Неизменяемая команда, с которой запускается контейнер |
| `CMD ["..."]` | Аргументы по умолчанию (или команда, если ENTRYPOINT не задан) |
| `ENV`, `ARG`, `EXPOSE` | Переменные окружения, аргументы сборки, документирование портов |

### Подводные камни Dockerfile

**1. `FROM` обязательно должна быть первой инструкцией.**
Единственное исключение — `ARG` может стоять до неё. Если перед `FROM` стоит, например, `RUN` — сборка упадёт с ошибкой парсинга ещё до попытки что-либо собрать.

**2. Путь в `COPY` отсчитывается от контекста сборки, а не от расположения Dockerfile.**
Контекст — это последний аргумент команды `docker build` (обычно `.`). Если контекст и папка с Dockerfile — разные вещи, легко получить путаницу.

**3. По умолчанию Docker ищет файл `Dockerfile` *внутри* указанного контекста.**
```
docker build -t app ./src
```
Здесь `./src` — это контекст. Docker будет искать `Dockerfile` по пути `./src/Dockerfile`. Если реальный Dockerfile лежит в родительской папке — будет ошибка, файл не найдётся.
Решение — явно указать путь к Dockerfile флагом `-f`, если он не совпадает с контекстом:
```
docker build -t app -f ./Dockerfile ./src
```

**4. `.dockerignore` делает файлы невидимыми для `COPY`, но не останавливает сборку сразу.**
Файлы, перечисленные в `.dockerignore`, не попадают в контекст сборки вообще — для Docker их как будто не существует. Сборка при этом стартует нормально (`FROM`, `WORKDIR` отработают), но **упадёт именно на той инструкции `COPY`**, которая пытается скопировать игнорируемый файл — с ошибкой вроде `"file.txt": not found`. Это не warning, а полноценная ошибка, прерывающая сборку.

**5. `COPY` сам создаёт нужные директории — не нужно заранее делать `mkdir`.**
Если путь назначения включает несуществующие папки, Docker создаст их автоматически.

**6. Порядок `COPY`/`RUN` критичен для кэширования слоёв.**
Каждый слой кэшируется. Если скопировать сразу все файлы разом (например, и `app.py`, и `requirements.txt`) одной инструкцией `COPY`, то изменение **любого** из них инвалидирует этот слой — а вместе с ним и все последующие, включая `RUN pip install`. В итоге зависимости переустанавливаются заново при каждой пересборке, даже если сам список зависимостей не менялся.
Правильный порядок:
```
COPY requirements.txt requirements.txt
RUN pip install -r requirements.txt
COPY app.py app.py
```
Так изменения в коде приложения не трогают кэш установки зависимостей — пересобирается только то, что реально изменилось.

**7. Удаление файла в отдельном `RUN` не уменьшает размер образа.**
Образы Docker строятся слоями, и слои **накапливаются**, а не заменяют друг друга. Если файл добавлен в одном слое (`COPY`), а удалён в следующем (`RUN rm file`) — физически он всё ещё лежит в предыдущем слое, просто скрыт в финальной файловой системе. Итоговый размер образа = сумма размеров всех слоёв, удаление ничего не "вычитает".

**8. `ENTRYPOINT` + `CMD` — это связка "команда + аргументы по умолчанию".**
`CMD` при наличии `ENTRYPOINT` работает как аргументы по умолчанию:
- `docker run <образ>` без своих аргументов → используются значения из `CMD`
- `docker run <образ> свой_аргумент` → полностью заменяет `CMD`, но не трогает сам `ENTRYPOINT`

Пример: чтобы контейнер работал и с аргументом, и без (подставляя дефолт), достаточно задать:
```
ENTRYPOINT ["bash", "script.sh"]
CMD ["world"]
```

**9. Exec-форма и shell-форма — обе валидны.**
`["bash", "script.sh"]` (JSON-массив) и `bash script.sh` (просто строка) — оба варианта рабочие и не вызывают ошибку сборки. Разница в том, как команда обрабатывается (через shell или напрямую), а не в валидности синтаксиса.

**10. Инструкции регистронезависимы, но по конвенции пишутся заглавными.**
`copy` сработает так же, как `COPY`. Ошибки не будет, но это не принятый стиль.

**11. Перенос команды на несколько строк через `\` — стандартный синтаксис, не ошибка.**
```
RUN apt-get update \
    && apt-get install -y curl \
    && apt-get clean
```
Это одна логическая команда для Docker, просто визуально разбитая на строки.

### Сборка

```
docker build -t <имя> .
docker build -t <имя> -f <путь_к_Dockerfile> <контекст>
```

## Часть 3. Шпаргалка по коротким флагам

| Флаг | Расшифровка | Что делает |
|---|---|---|
| `-d` | detached | Запуск в фоновом режиме, терминал не занят |
| `-i` | interactive | Держит stdin контейнера открытым |
| `-t` | tty (в `run`) | Выделяет псевдотерминал (для красивого интерактивного вывода) |
| `-it` | interactive + tty | Комбинация двух флагов, нужна для полноценной интерактивной сессии (например, `bash`) |
| `-p` | publish (port) | Проброс порта: `-p <host_port>:<container_port>` |
| `-v` | volume | Монтирование тома: `-v <host_path>:<container_path>` |
| `-e` | environment | Задать переменную окружения: `-e KEY=value` |
| `--name` | — | Задать имя контейнеру вручную |
| `--rm` | remove | Автоматически удалить контейнер после остановки |
| `-a` | all | Показать все объекты, включая остановленные/промежуточные (`ps -a`) |
| `-q` | quiet | Вывести только ID, без таблицы |
| `--no-trunc` | no truncate | Не обрезать длинные ID/хеши в выводе |
| `-t` | tag (в `build`) | Задать имя:тег собираемому образу |
| `-f` | file / force | Путь к Dockerfile (в `build`) **или** принудительное действие (в `rm`, `rmi`) — смысл зависит от команды |

**Важный нюанс:** одна и та же буква флага может значить разное в разных командах (`-t` в `run` — это tty, а `-t` в `build` — это tag; `-f` в `rm` — force, а `-f` в `build` — путь к файлу). Смысл флага всегда привязан к конкретной команде, не переносится по аналогии.
